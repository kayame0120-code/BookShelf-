# BookShelf 技術決定書

要件シートで決まっていなかったこと・実装の途中で変えたことについて、**何を決めたか**と**なぜそうしたか**を載せる。決めた内容の細部（文言・ルール・遷移先）は機能仕様書に書き、ここでは参照だけにする。

- 理由の書き方: 要件シートの記述、QUESTIONS.md の裁定、コード内のコメント、旧docs（旧機能仕様書・旧発注書・旧検品表・決定記録）のいずれかに記録がある場合だけ、その出典とともに書く。旧docsの記録は、内容が現在の実装と同じ場合だけ理由として採用し、違う場合は食い違いとして書く。記録が無いものは「記録なし」と書き、推測で補わない
- 旧docsの出典の書き方: 旧 `docs/01_機能仕様書/` は「旧仕様 ファイル名:行」、旧 `docs/02_発注書/` は「旧発注書 ファイル名:行」、旧 `docs/03_検品表/` は「旧検品表 ファイル名:行」。旧docsはこの文書群への置き換えと docs の整理で削除・変更されるため、出典の行番号はコミット `4fe0e82` 時点のファイルを指す（`git show 4fe0e82:docs/01_機能仕様書/books.md` のように履歴から参照できる）
- 基準コミット: 発注書95の修正（コミット `4fe0e82`）を含む
- 番号: TD-01〜TD-09 は要件シート シート2「設計タスク一覧」の9項目への回答、TD-10 以降はそれ以外の決定

## 目次

1. 設計タスク一覧への回答（TD-01〜TD-09）
2. 要件からの変更・追加の決定（TD-10〜TD-21・TD-31〜TD-33）
3. 提供Blade（モック）からの変更（TD-22、15ファイル）
4. 決定していない現状の挙動（TD-23〜TD-30・TD-34）
5. 未解消の記録（QUESTIONS.md）
- 付録: 完成条件の照合

## 1. 設計タスク一覧への回答

要件シート シート2「設計タスク一覧」（`D16`〜`D24`）の9項目に、実装で決めた内容を対応させる。

### TD-01 画面遷移の設計（シート2 E16）

| 決めたこと | 詳細 |
|---|---|
| 書籍・レビューの登録・更新・復元が成功したら、その書籍の詳細画面へ | 機能仕様書 1-3・1-4・1-5・3章 |
| 削除が成功したら一覧へ（書籍→書籍一覧）。レビューの削除は書籍詳細へ | 機能仕様書 1-5・3章 |
| ジャンル・読書計画の操作は、成功・失敗とも各一覧へ | 機能仕様書 2章・8章 |
| お気に入り・いいね・通知の既読化は、元の画面に戻る | 機能仕様書 3章・4章・9章 |
| 入力エラーは、入力値を残したまま元のフォームへ | 機能仕様書 0章 |
| 未ログインで保護された画面を開くとログイン画面へ。ログイン後は開こうとした画面へ | 機能仕様書 0章 |
| ログイン・会員登録の後は `/books`、ログアウトの後は `/` | 機能仕様書 6章 |

理由:
- 成功時の移動先を書籍一覧・書籍詳細・ジャンル一覧・読書計画一覧にそろえたのは、提供Bladeでフラッシュを表示する欄を持つ画面がこれらだけだから（旧仕様 books.md:185、旧仕様 reading_plans.md:381、旧発注書 発注書_02_書籍CRUD.md:121）
- ログイン後の移動先を `/books` にしたのは、Laravel既定の `/home` がこのアプリに無く404になるため（旧仕様 auth.md:355、旧発注書 発注書_01_土台認証.md:87）
- 削除済みの書籍の編集・更新・削除のURLを404にしたのは、編集ボタンが出ない画面へ直接アクセスさせないため（旧仕様 books.md:67）

### TD-02 フラッシュメッセージの設計（シート2 E17）

| 決めたこと | 詳細 |
|---|---|
| 成功時は「〇〇を△△しました」の形（句点なし）で、移動先の画面上部に緑の帯で表示 | 機能仕様書 1〜3章・8章 |
| 失敗をフラッシュで出すのはジャンルの削除拒否だけ（赤の帯）。それ以外の失敗は、入力エラーの表示・403・404画面で伝える | 機能仕様書 2章 |
| お気に入り・いいね・通知の既読化はメッセージを出さない（元の画面に戻るだけ） | 機能仕様書 3章・4章・9章 |
| ログイン・会員登録・ログアウトはメッセージを出さない | 機能仕様書 6章 |

理由:
- お気に入りは、お気に入り一覧のBladeにメッセージを表示する欄が無く、同じ操作が書籍詳細とお気に入り一覧の2つから呼ばれるため、片方だけメッセージが出る状態を避けて出さない方に統一した。状態はボタンの見た目で表す。いいねも同じ方針（旧仕様 favorites.md:95-97、旧仕様 reviews_likes.md:143）
- 通知の既読化も同じ方針に合わせ、未読バッジが消えることで状態を表す（旧仕様 notifications.md:132-136）
- ログイン・会員登録の画面のBladeには、メッセージを読み出すコードが無い（旧仕様 auth.md:339）
- 成功時の文言の形（「〇〇を△△しました」）にした理由は記録なし

### TD-03 認可ルールの設計（シート2 E18）

| 決めたこと | 詳細 |
|---|---|
| Policy を作る対象は書籍・レビュー・読書計画の3つ | 全体仕様書 5章 |
| 書籍は登録者本人だけが編集・削除・復元できる。削除済みの書籍は編集・削除できず、復元だけできる | 機能仕様書 1-4・1-5 |
| レビューは投稿者本人だけが編集・削除できる | 機能仕様書 3章 |
| 読書計画は作成者本人だけが操作でき、完了した計画は編集・読了できない（削除はできる） | 機能仕様書 8章 |
| ジャンルには所有者を置かず、ログイン中の会員なら誰でも登録・編集・削除できる | 機能仕様書 2章 |
| 紐づく書籍があるジャンルは、赤いメッセージを出して削除を拒否する。アプリ側の確認とDBの制約の二重で止める | 機能仕様書 2章 |
| 通知は自分宛てだけを既読にできる（Policy ではなくコントローラーで確認） | 機能仕様書 9章 |
| 権限が無いときは403 | 機能仕様書 0章 |

理由:
- 他人の書籍の編集を403にすること、紐づく書籍があるジャンルの削除を拒否することは、シート2 F18 のヒアリング例と同じ方針
- 通知の既読化は、要件シート シート7 の「他人の通知IDを直接指定された場合は403」に従う。所有者で絞って探す方法だと見つからずに404になるため、通知を取得してから送り先を確かめて403を返す（旧仕様 notifications.md:130）
- マイ読書レポートは、自分のデータしか見ない画面なので Policy を作らず、自分のレビューだけを取り出すことで他人のデータの混入を防ぐ（旧発注書 発注書_09_読書レポート.md:43）
- 完了した読書計画の読了を Policy で拒否するのは、画面にボタンが出ない状態で直接送られた場合の防御（旧仕様 reading_plans.md:199、旧発注書 発注書_11_読書計画CRUD.md:153）
- ジャンルに所有者を置かない方針は旧仕様 genres.md:19 と要件シート シート10 G16 にあるが、理由は記録なし

### TD-04 バリデーションルールの設計（シート2 E19）

| 決めたこと | 詳細 |
|---|---|
| フォームごとに FormRequest を分け、ルールとエラー文言を同じクラスに書く（会員登録だけは Fortify の `CreateNewUser` に書く） | 機能仕様書 1-3・2章・3章・6章・7章・8章 |
| タイトル・著者は必須で255文字以内、説明・コメントは1000文字以内 | 機能仕様書 1-3・3章 |
| ISBN は数字13桁で、削除済みの書籍を含めて重複不可。編集では自分自身を重複チェックから除く | 機能仕様書 1-3 |
| 画面の書籍登録では ISBN・出版日を任意、公開APIでは必須（TD-11） | 機能仕様書 1-3・7章 |
| 読書計画は、同じ書籍で進行中の計画がある場合だけ作成を拒否する | 機能仕様書 8章 |

理由:
- ISBN を13桁固定で一意にすること、編集時に自分自身を除くことは、シート2 F19 のヒアリング例と同じ方針
- FormRequest への分離は、要件シート シート3・シート8 の要件（旧仕様 public_api.md:293）
- 読書計画の重複を、プルダウンから除くのではなく送信後に判定するのは、完了・期限切れの計画しか無い書籍は再登録できるべきで、プルダウンで除くと再登録できる書籍まで消えるため（旧仕様 reading_plans.md:185）
- 書籍一覧の検索条件（キーワード・ジャンル・並び順）に入力ルールを置かないのは、要件シートが「不正な値でもエラーにしない」と定めているため（旧発注書 発注書_07_検索フィルタソート.md:31）
- ISBN検索の13桁チェックを FormRequest にせずコントローラーで行うのは、確かめる値がURLの1つだけで、エラーを表示する画面も無いため（旧仕様 books.md:167）
- 文字数の上限（255文字・1000文字）の理由は記録なし

- 共通文言の項目名の日本語訳が無い項目がある点は TD-26

### TD-09 読書計画・リマインダー通知の設計（シート2 E24・応用）

| 決めたこと | 詳細 |
|---|---|
| 状態は 進行中・完了・期限切れ の3つ。完了は「読了する」操作で、期限切れは自動 | 機能仕様書 8-1 |
| 期限切れにするのは、期日の3日後の0:00 | 機能仕様書 9-2 |
| 通知は期日の3日前・当日・3日後の3回。毎日7:00に送る。3日後の通知は期限切れの計画にも送る | 機能仕様書 9-2 |
| 期限切れの計画も編集・読了・削除できる。完了した計画は削除だけできる | 機能仕様書 8-1・8-2 |
| 同じ書籍で進行中の計画は1つまで | 機能仕様書 8章 |
| 期日は今日以降だけ指定できる | 機能仕様書 8章 |
| 書籍が削除されても、読書計画と通知は書籍名とともに残る | 機能仕様書 8-2・9-2 |
| 通知はLaravel標準の通知（DB保存）を使い、メールは送らない | 機能仕様書 9章 |

理由:
- 期限切れ後も編集・読了できることは、要件シート シート11 H15 の記述
- 3日後の通知を期限切れの計画にも送るのは、0:00 の処理で先に期限切れへ変わった計画にも通知を届けるため（`app/Console/Commands/SendReadingPlanReminders.php:37-38` のコメント）
- 書籍が削除されても計画を表示するのは、論理削除済みの書籍に紐づく計画も一覧・編集で表示するため（`app/Models/ReadingPlan.php:40` のコメント）
- 通知にLaravel標準を使うことは、要件シート シート11 H16 の記述
- 重複の判定を進行中の計画だけにするのは、完了・期限切れの計画しか無い書籍は再登録できるようにするため（旧仕様 reading_plans.md:250）
- 期限切れにする処理は進行中の計画だけを対象にするので、何度実行しても結果が変わらない（旧仕様 reading_plans.md:290）
- 「期日の3日後に期限切れ」「期日は今日以降」にした理由は記録なし
