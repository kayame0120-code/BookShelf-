# 発注書 13 — コード品質リファクタ（型宣言・PHPDoc・Collection化）

**対象走行**: 走行⑬（第6週）
**出典**: 要件シート.xlsx シート3 R28〜R30（★型宣言・★PHPDoc・★Collectionメソッド活用）
**対の検品表**: `docs/03_検品表/13_品質リファクタ.md`
**前提**: 走行①〜⑫が合格・確定済み。本走行は新機能を追加せず、既存の実装ファイルにコード品質基準を遡及適用する。

---

## 0. スコープ

### やること

1. 全既存Controller（`app/Http/Controllers/*.php`・`app/Http/Controllers/Api/V1/*.php`）の全メソッドに、引数と戻り値の型宣言を付与する。
2. 全既存Model（`User`・`Book`・`Genre`・`Review`・`ReadingPlan`）のリレーションメソッドに、`HasMany`・`BelongsTo`・`BelongsToMany` といった具体的な戻り値型を宣言する。
3. 全既存FormRequest・Policyクラスの全メソッドに型宣言を付与する。
4. 各コントローラーのアクションメソッド（`index`/`store`/`update`/`destroy` を含む）と、`ReportController` の集計ロジックのように処理内容が自明でないメソッドにPHPDocを付与する。
5. `ReportController` について、手続き的な `foreach` が紛れていないかを再確認し、あれば `map`/`filter`/`groupBy`/`flatMap` といったCollectionメソッドに置き換える。
6. 他のController・Modelについても、手続き的な `foreach` で実装されている箇所があれば、既存の入出力仕様を変えない範囲でCollectionメソッドに置き換える。

### やらないこと

1. 新規機能の追加、ルーティングの変更、DBスキーマの変更。
2. 型宣言・PHPDoc・Collection化以外の理由でのロジック変更（挙動を変えるリファクタは行わない。既存の入出力仕様を壊した場合は差し戻し対象とする）。
3. PHP Enumの新規導入。`ReadingPlanStatus`（発注書11）・`NotificationTiming`（発注書12）は既に導入済みであり、本走行では新規Enumを作らない（決定台帳D6参照）。
4. Sanctum・Schedule/ConsoleCommand・DB Transaction・Notification facade・外部API連携の新規導入。これらはそれぞれ対応する発注書07・08・10・11・12で既に実装済みのため、本走行の対象外とする（決定台帳D6参照）。
5. 自動テストコード（PHPUnit）の新規作成。走行⑭の範囲。ただし既存のテストがあれば、リファクタ後に全て通過することを確認する（§4）。

## 1. 型宣言の基準

- 例: `public function index(): View`、`public function store(BookStoreRequest $request): RedirectResponse`。
- モデルのリレーションメソッドは `public function books(): HasMany` のように具体的な戻り値型を宣言する（`Relation` のような抽象型は使わない）。
- 引数にも可能な限り型を付与する（FormRequestの引数や、既存のルートモデルバインディングで既に型が付いている箇所は、そのままでよい）。

---

## 2. PHPDocの基準

「主要なメソッド」とは、各コントローラーのアクションメソッドと、`ReportController` の集計ロジックのように処理内容が自明でないメソッドを指す。単純なgetter/setterや1行で完結するメソッドには必須としない。記述内容は処理内容の要約1〜2行、`@param`、`@return` とする。

---

## 3. Collection化の基準

特に `ReportController` で徹底する（発注書09の実装時点で既にCollectionメソッドで実装されているはずだが、本走行で再確認する）。対象は「配列やコレクションに対する繰り返し処理」であり、単純なif分岐やDBクエリの発行自体をCollectionメソッドに置き換える必要はない。

## 5. 禁止事項

1. 挙動を変えるリファクタを行わない。既存の検品済み動作を壊さない。
2. Bladeファイルを変更しない。
3. 新規Enum・新規パッケージの導入を行わない（決定台帳D6参照）。
4. 本発注書に明記されていないロジックを独自に追加しない。
5. `main` ブランチへ直接コミットしない。
