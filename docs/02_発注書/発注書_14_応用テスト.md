## 2. 正本の確定値（この値でテストを書く）

正本と実装の照合済みの確定値を以下に記す。テストはこの確定値で書く。

### 2-1. ISBN / published_date（nullable）

- 応用では isbn・published_date を必須から任意（nullable）へ変更している。値がある場合のみ桁数・一意性・日付形式を検証する。必須チェックのメッセージは存在しない。
- テストは「空のまま登録・更新が成功する」「値がある場合のみ13桁・一意性・日付形式チェックが働く」で書く。空POSTで isbn/published_date の必須エラーを期待するテストは書かない。

### 2-2. API認証（Sanctum必須・401）

- 公開APIの書き込み系（POST/PUT/DELETE）3本に `auth:sanctum` 必須。読み取り系（GET 2本）は認証不要。
- テストは `Laravel\Sanctum\Sanctum::actingAs($user)` で認証してから書き込み系を検証する。未認証時は401を期待する。
- 401応答は `{"message": "認証が必要です。"}`。403応答は `{"message": "この操作を実行する権限がありません。"}`。テストはこれらを `message` キーの日本語文言で確認する。

### 2-3. レビュー件数（rand(2,4)・可変）

- ReviewSeeder はレビュー件数を各書籍2〜4件（`rand(2, 4)`）でランダム化している。評価は1〜5の全範囲、投稿者もランダム。
- テストはレビュー件数を固定値（32等）で一致確認してはならない。件数固定を前提としない検証（各書籍のレビューが2件以上4件以下の範囲に収まる・関連の整合など、非決定性に依存しない観点）で書く。

### 2-4. 通知バッチ three_days_after の対象status（in_progress ＋ expired）

- `three_days_after` の対象statusは完了以外（`in_progress` ＋ `expired`）。`three_days_before`・`on_due_date` は `in_progress` のみ。
- 理由: 7:00のリマインダーバッチ実行時点で、0:00の自動失効バッチにより該当計画が既に `expired` へ切り替わっているため、`in_progress` 限定だと期限切れ計画への通知が漏れる。
- テストは `three_days_after` について、`expired` の計画にも通知が作成されることを確認する。`three_days_after` を「in_progress のみ」で書くとシードシナリオ（計画#3）で再現しない。

### 2-5. 自動失効バッチの境界（本日の3日前ちょうど1日のみ = 等値）

- 対象は `target_date` が本日の3日前にちょうど一致し、かつ `in_progress` の計画のみ。本日の2日前は対象外、本日の4日前以前も対象外、当日・未来も対象外。
- テストは「本日の3日前ちょうどが expired に変わる」「本日の4日前は in_progress のまま変わらない」「本日の2日前は変わらない」の3点を書く。特に4日前が変わらないことの確認は、等値実装を強制する行として必ず含める。

### 2-6. シードシナリオ（ReadingPlanSeeder・6件）

`Carbon::today()` 起点で動的設定。ユーザーは投入順で 山田太郎=ID1、鈴木花子=ID2（全5名）。「計画#1〜#6」は投入順の計画ID。

- 計画#1: `target_date = today+3` / `in_progress` → 3日前リマインダー対象
- 計画#2: `target_date = today` / `in_progress` → 当日リマインダー対象
- 計画#3: `target_date = today-3` / `in_progress` → 0:00失効バッチで expire化 かつ 7:00リマインダーで three_days_after 通知対象（二重シナリオ）
- 計画#4: `target_date = today+7` / `in_progress` → リマインダー対象外
- 計画#5: `target_date = today-10` / `completed` / `completed_at = today-5` → 完了済み
- 計画#6: 所有者=鈴木花子（ID2） / `target_date = today+5` / `in_progress` → 山田太郎ログイン中に `/reading-plans/6/edit` 直打ちで403確認用

## 3. 粒度の適用（CLAUDE.md 13-A章）

各対象機能について、13-A章の4観点を該当する限りすべて実装する。

- 正常系: 成功後の結果と遷移先まで確認する。
- 異常系: 入力項目1つにつき1本。まとめない。
- 境界値: 桁数・日付・件数の「ちょうど」を両側で確認する（ISBN13桁ちょうど/12桁・14桁、失効の3日前/4日前など）。
- 認可失敗: 他人のリソース403・未認証401（またはログインリダイレクト）を、HTTPメソッドごとに個別に確認する。

文言の確認は13-A-2に従う。確定文言（§2の日本語文言・シート8★の確定バリデーション文言・フラッシュ文言）は一字一致で確認する。文言が明記されていない箇所は、対応する入力項目に `$errors` のエラーが記録されていること（空でないこと）を確認し、その内容が英語の生エラーでないことを添える。文言未確定箇所は検品表の解釈ログに一覧として書き出す。

## 4. テストの方式（正本確定値）

- カバレッジ: 合格条件はカバレッジの数値ではなく、説明のつかない未カバー行がゼロであること（CLAUDE.md 13-A-4）。アプリが使う機能の未カバー行はすべてテストで潰す。残してよいのは除外リストに理由付きで載せた行のみ。`sail artisan test --coverage` の出力は中略せず全クラスの行を採取する。
- 外部APIテスト（ISBN検索）: `Illuminate\Support\Facades\Http` の `Http::fake()` でモック化し、実際のGoogle Books APIを呼ばない。
- ISBN検索のエラー応答キーは `message` で統一済み。テストはエラー応答を `message` キーで確認する（422「ISBNは13桁の数字で入力してください」／404「該当する書籍が見つかりませんでした」／502「書籍情報の取得に失敗しました」）。
- Sanctum認証テストは `Laravel\Sanctum\Sanctum::actingAs($user)` を使用する。
- 自動失効バッチ・リマインダーバッチのテストは、`Carbon::setTestNow()` またはシード済みデータを用い、実行タイミングに依存しない形で書く。
- 自動失効バッチの境界テストは、§前提の等値実装（`subDays(3)` の等値）が完了していることを確認してから実行する。

## 7. 既存の失敗テストの扱い

応用の仕様変更で失敗している既存テストは、正本準拠で書き直す。

- API書き込み系が未認証で401になっているテスト → `Sanctum::actingAs` で認証してから検証する形に書き直す。
- 空POSTで isbn/published_date の必須エラーを期待しているテスト → nullable前提（空で成功）に書き直す。
- レビュー件数を固定値で一致確認しているテスト → 範囲・存在・関連の整合で書き直す。
- 削除済み書籍のバナー表示を期待しているテスト → 走行⑮・基本機能の確定挙動に合わせて書き直す。
