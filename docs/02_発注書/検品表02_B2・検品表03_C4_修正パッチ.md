# 検品表02 B-2 ／ 検品表03 C-4 修正パッチ

`docs/03_検品表/02_書籍CRUD.md` の B-2 行、`docs/03_検品表/03_レビューお気に入りいいね.md` の C-4 行を以下に差し替える。他の行は変更不要。

## 変更理由

現行の確認方法（`curl`による生のHTTPリクエスト）は、書き込み系ルート（POST/PUT/DELETE/PATCH）の未認証時挙動を検出できない設計になっている。

Laravel標準の`web`ミドルウェアグループでは、`VerifyCsrfToken`が`auth`ミドルウェアより先に評価される。CSRFトークンを持たない生の`curl`リクエストは、認証状態に関わらず`VerifyCsrfToken`の時点で`419`を返して処理が打ち切られる。そのため「未認証だから`/login`へ302リダイレクトされる」という`auth`ミドルウェア固有の挙動は、この検証方法では原理的に観測できない。

一方、PHPUnitのFeatureテストは`Illuminate\Foundation\Http\Middleware\VerifyCsrfToken::runningUnitTests()`により、テスト実行環境下でCSRF検証が自動的にスキップされる。これにより`auth`ミドルウェアの挙動だけを他の要因から切り離して検証できる。

（走行②③の再検品で、4本すべてのcurlが419を返す事象をCCが正しく検出・報告し、QUESTIONS.mdへ記録したことを受けて本パッチを発行する。実装・検品表いずれの不備でもなく、確認方法の設計を修正するもの。）

| B-2 | `books.create` `books.store` `books.edit` `books.update` `books.destroy` `books.restore` は未ログインで`/login`へ302リダイレクトされる | GET系（create/edit）は`curl -I`で確認。書き込み系（store/update/destroy/restore）はFeatureテストで`actingAs()`を使わずに`post()`/`put()`/`delete()`/`patch()`を実行し`assertRedirect('/login')`で確認（生curlはCSRF検証が先行するため419になり検証不能） | 差し戻し |

## 検証コード例

```php
// tests/Feature/ScreenAccessTest.php または BookCrudTest.php に追加
public function test_guest_cannot_perform_book_write_actions(): void
{
    $book = Book::factory()->create();

    $this->post(route('books.store'), [])->assertRedirect('/login');
    $this->put(route('books.update', $book), [])->assertRedirect('/login');
    $this->delete(route('books.destroy', $book))->assertRedirect('/login');
    $this->patch(route('books.restore', $book))->assertRedirect('/login');
}
```

```php
// tests/Feature/ReviewLikeTest.php に追加
public function test_guest_cannot_like_review(): void
{
    $review = Review::factory()->create();

    $this->post(route('reviews.like', $review))->assertRedirect('/login');
}
```

これらのテストがPASSした時点で、②B-2・③C-4とも解消とする。curlの419出力は「認証チェックより前段のCSRF保護が正しく機能している」ことの証拠として証拠ファイルに残してよいが、B-2/C-4の判定根拠としては上記Featureテストの結果を用いる。
