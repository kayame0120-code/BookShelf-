# 共通ルール

`docs/02_発注書/` の13本と `docs/03_検品表/` の13本に共通してかかる規則をここにまとめる。各文書はこの1枚を指し、同じ内容を繰り返さない。

各文書に固有の内容（担当する機能の範囲・完成条件・対象ファイル・確定値・判定条件）は、それぞれの文書の中に具体値で書く。

`CLAUDE.md` はリポジトリ直下にある、実装を行うAIの作業規約である。この文書と `CLAUDE.md` の両方が実装AIにかかる。この文書は `docs/` の中の進め方を定め、`CLAUDE.md` はリポジトリ全体の作業規約を定める。

---

## 1. 発注書に共通する規則

### 1-1. 着手の前に

- 対象の発注書と、同じ番号の検品表を先に読む。検品表が合格の基準であり、発注書に書かれていても検品表に無い作業は完成条件に含まれない。
- 発注書が前提として挙げているものが実際に存在するかを、着手の前に現物で確認する。存在しなければ着手せず、1-3に従って止まる。

### 1-2. 書かれていないことをしない

- 発注書に明記されていないロジック・画面・入力項目・ルートを追加しない。
- 発注書が対象として挙げていないファイルを変更しない。
- 発注書の指定と違う実装をしたほうがよいと考えた場合も、その場で決めずに1-3に従って止まる。

### 1-3. 定義が無い場面に当たったとき

発注書にもこの文書にも `CLAUDE.md` にも定義が無い事項に当たったら、その場で決めずに `QUESTIONS.md` へ次の4つを記入し、その作業を止めて次の作業へ移る。

| 欄 | 書く内容 |
|---|---|
| 発生日 | |
| 対象の発注書 | ファイル名 |
| 止まった箇所 | ファイル・行・実行したコマンド |
| 解釈の候補 | 2案以上。それぞれ何が変わるかを添える |

1案しか思いつかない場合も、その1案を採用せずに記入して止まる。

### 1-4. 変更してよい範囲

- `resources/views/` の Blade は、発注書がファイル名を挙げて変更を指示したものだけを変更する。それ以外は1文字も変更しない。提供モックは固定された資料であり、勝手な改変は資料違反として扱う。
- 既存の動作を壊す変更をしない。既に合格している内容が動かなくなった場合は差し戻しの対象になる。
- フレームワークやパッケージが標準で追加する定義を、その機能を使わないという理由だけで削除しない。使わない機能への対処は、呼び出さないことで行う。

### 1-5. コミット

- `main` ブランチへ直接コミットしない。
- コミットメッセージは、何をしたかが日本語または英語で分かる文にする。`wip`・`fix` 単独・`update` のような内容の分からないものにしない。
- コミットの前に整形の確認（`sail bin pint`）を実行し、`sail bin pint --test` で指摘が0件であることを確かめる。

### 1-6. 完了したときに報告するもの

発注書ごとの固有の報告に加えて、次を必ず報告する。

- 作業ブランチ名と最終のコミットID
- `sail bin pint --test` の出力
- `QUESTIONS.md` に追記した行の有無

## 2. 検品表に共通する規則

### 2-1. 証拠を集めるときの条件

- 実装を行ったセッションとは別の、文脈を持たない新しいセッションで証拠を集める。
- 証拠を集めるセッションに渡してよいのは次の4つだけである。実装時の会話・設計の経緯は渡さない。

| 渡してよいもの |
|---|
| `CLAUDE.md`（自動で読み込まれる） |
| この文書 |
| 対象の検品表と、同じ番号の発注書 |
| 実装済みのコード |

### 2-2. 証拠には判定を書かない

証拠は、検品表の各行に対応する生の実行結果だけを書く。コマンドの出力、DBの照会結果、画面で見た文字列そのもの、ソースコードの該当箇所の引用がこれにあたる。

次の語を証拠に書かない。

```
YES  NO  PASS  FAIL  合格  不合格  正しく動作した  問題ない  想定通り
```

行の結果が期待値と違う場合も、違うと書かずに、実際に得られた出力をそのまま貼る。

### 2-3. 判定は別の場所で行う

判定（YES/NO）は、証拠と検品表を突き合わせて、証拠を集めたセッションの外で行う。

- 全行に判定と、その根拠になった生の記録を添える。根拠の無いYESは無効とし、根拠不足としてNOにする。
- 1行でもNOがあれば、その番号は不合格とする。
- 判定を後から書き換えない。検品表を直した場合は、証拠を取り直してから判定し直す。

### 2-4. 期待値の基準

- 期待値は、最終の実装コード1点を基準にする。作りかけの途中の状態を期待値にしない。
- 同じ番号の検品結果は、すべて同じコミットIDを指す。
- 期待値が実装の初期データと矛盾していないことを、検品表を作る段階で確かめる。初期データのうち実行のたびに変わる部分は、固定の値で一致を求めない。

### 2-5. 確認方法の書き方

- 全行が1条件1行で、YESかNOで判定できること。
- 全行に「確認方法」と「期待値」があること。
- 確認方法は、その手段で本当に確認できるものにする。外部からの呼び出しで確かめられない挙動は、テストコードでの確認に置き換える。

### 2-6. 差し戻し

不合格になった場合、指摘を全量まとめて1回で出し、修正も全量を1ラウンドで行う。指摘の小出し・修正の小出しをしない。修正のあとは、その番号の全行を最初から実行し直す。

## 3. 文書の書き方に共通する規則

### 3-1. 使わない言葉

次の語を使わない。曖昧なまま実装や判定に渡ると、判断が人によって変わる。

```
適切に  必要に応じて  検討  基本的に  TBD  など  等
```

学校から配布された原文をそのまま引用する場合はこの限りではないが、引用であることを明記する。

### 3-2. その1枚で完結させる

- 過去の版との違い、変更の経緯、いつ誰が直したかを書かない。各文書は、初めて読む人がそれ1枚で理解できる内容にする。
- 内部の文書番号や章番号だけで説明を済ませない。内容と理由を本文に書く。他の文書を指すときも、何が書かれているかを1行で添える。

### 3-3. 移り変わるものに依存しない

ファイルを特定するとき、コミット時点のファイル名や行番号に依存しない。

| 対象 | 書き方 |
|---|---|
| テーブル | テーブル名とカラム名で書く。マイグレーションのファイル名では書かない |
| 画面 | 画面IDとURLで書く |
| ルート | HTTPメソッドとURIで書く |
| クラス | 名前空間を含むクラス名で書く |
| コードの位置 | クラス名とメソッド名で書く。行番号では書かない |
