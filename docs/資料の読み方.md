# 資料の読み方

`docs/` を初めて開いた人のための案内。ここにある文書が何で、どの順に読むと分かるかを示す。

BookShelf は書籍を登録・共有し、レビュー・お気に入り・いいねで評価を集める読書管理アプリである。Laravel で作られており、実装は完了している。

---

## 1. 用語

| 用語 | 意味 |
|---|---|
| 仕様書 | このアプリが何をどう動かしているかを記述した3本（全体仕様書・機能仕様書・技術決定書）。実装コードから書き起こしたもの |
| 発注書 | 実装を行うAIへの指示書。「何を作るか」を具体値で書く |
| 検品表 | 合格基準を1条件1行のYES/NO形式で並べた事前の基準。発注書と対で作る |
| 証拠 | 検品表の各行に対応する生の実行結果。コマンドの出力、DBの照会結果、画面で見た文字列そのもの、コードの該当箇所の引用がこれにあたる。判定は含まない |
| 検品結果 | 証拠を検品表と突き合わせて出した最終の判定 |
| 機能軸 | 発注書・検品表・検品結果に振る 00〜12 の番号の基準。アプリの機能の単位で番号を振る方式 |
| 提供資料 | 学校から配布されたもの。画面の見た目を用意したBladeモックと、作るものを定めた要件シートの2つ |

---

## 2. どこに何があるか

| 場所 | 役割 |
|---|---|
| `00_提供資料/` | 学校から渡された資料がどこにあり、このアプリとどういう関係にあるかの案内。資料の実体は置かない |
| `01_仕様書/` | 実装されたアプリの姿を記述した3本。`docs/` 全体で唯一、内容の基準になる場所 |
| `02_発注書/` | 各機能で何を作るかを、実装を行うAIが質問なしで着手できる粒度で書いたもの。13本 |
| `03_検品表/` | 各機能の合格基準を、判定する人によって結果が変わらない形で事前に定義したもの。13本 |
| `04_検品結果/` | 検品表に照らして出した判定。13本と、カバレッジの除外リスト |
| `共通ルール.md` | 発注書13本と検品表13本に共通してかかる規則。各文書はこの1枚を指し、同じ内容を繰り返さない |
| `番号一覧.md` | 00〜12 の番号が何を指すかの一覧。範囲と完成基準が13件ぶん載っている |
| `資料の読み方.md` | この文書 |

---

## 3. 読む順

**アプリの中身を知りたい**

1. [全体仕様書](01_仕様書/全体仕様書.md) — 画面18枚・ルート52本・テーブル13個の一覧と、テーブル定義。まずここで全体を見渡す
2. [機能仕様書](01_仕様書/機能仕様書.md) — 機能ごとの動き。入口・権限・入力ルールとエラー文言・成功時・失敗時
3. [技術決定書](01_仕様書/技術決定書.md) — そう作った理由と、学校の要件と実装が違う箇所

**作る側・確かめる側として関わる**

1. [共通ルール](共通ルール.md) — 全体にかかる規則
2. [番号一覧](番号一覧.md) — 担当する番号の範囲と完成基準
3. `02_発注書/` と `03_検品表/` の、その番号の2本。検品表が合格の基準であり、発注書に書かれていても検品表に無い作業は完成条件に含まれない

**学校の配布物との関係を知りたい**

1. [提供資料の所在](00_提供資料/提供資料の所在.md) — Bladeモックの取得先と、要件シートの所在

## 4. 食い違ったときにどれを採るか

| 場面 | 採るもの |
|---|---|
| 文書と実装コードが食い違う | 実装コード。仕様書3本は実装から書き起こしたものであり、実装が現在の姿である |
| 仕様書と発注書・検品表が食い違う | 仕様書3本 |
| 発注書と検品表が食い違う | 検品表。合格の基準はこちらにある |
| 提供資料と実装が食い違う | 実装。違いとその理由は技術決定書に載っている |

---

## 5. 番号の対応

`02_発注書/` `03_検品表/` `04_検品結果/` は、同じ番号で1組ずつ対応する。番号は 00〜12 の13セットで、機能仕様書の章番号と同じである。

```
01_仕様書（3本）
   │ ここに合わせて書く
   ▼
02_発注書 00〜12 ──対── 03_検品表 00〜12
                           │ 実装コードを確認して証拠を集める
                           ▼
                       04_検品結果 00〜12
```
